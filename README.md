# SDF Hardware Accelerated Raymarcher

- Simple global primitives (box, rock, box with cutouts):
    - `Box` is simply a box SDF
    - `Rock` is a box that has been chipped away using plane intersections. Fully procedurally generated
    - `BoxWithCutouts` is a box SDF with subtracted cylinders on each axis.
    - Primitives apply their SDF to the global SDF using a 128^3 lookup texture (centered at the origin)
    - Lookup texture stores up to 4-intersecting primitives (texel type = `u32`, so primitive are represented using a `u8`)
- Simple local primitive (tree):
    - Local SDF is stored in a texture
    - Does NOT apply to the global SDF; instead, we just trace against the local SDF in the HWRT intersection test
- CPU side HWRT stuff (creating BLASes, TLAS generation)
- Chunk generation (CPU):
    - Chunks are generated by creating a density field. ``Vec<f32>``. Negative value signifies terrain / solid matter, positive values signify air
    - Density field is then converted to an SDF using the `Jump Flood Algorithm` (accelerated using Rayon)
    - Chunks are then converted to BLASes

## Rendering Techniques:
- Interesting material system using NonUniformIndexing to allow for varying materials (currently loads materials textures)
- Path traced ""reference"" (not physically accurate at all, rays do not follow PBR rules, not well sampled either). 1-2 bounces. can give pretty reflections
- VXGI that uses the global SDF as basis to create surfaces. Works somewhat okay for diffuse lighting, though for specular reflections, using the ray-traced reference yields much better results
    - Uses a 128^3 RGBA texture to store the resulting GI radiance
    - VXGI steps just blurs the image to higher and higher mips, then these mips are marched against when shading. Mip selection is proportional to input cone angle and distance

# Problems:
- Local SDF do not contribute to global SDF, meaning VXGI pass / other things that depend on the global SDF fail to capture the local SDF primitives
- Generating the BLAS bounds for the primitives is tedious. Ideally, this would be done automatically, and, *super ideally*, the bounds would be much tighter than what we have right now
- Needing to expand the BLAS bounds whenever we use "smooth" operators (`smin, smax`). Since the raymarcher only executes whenever we have a possible BLAS intersection, the bounds of the BLAS need to be relaxed to capture smooth blending effects between multiple primitives
- Bounds are not tight.
- Some effects are not possible due to the ray-volume intersection method. Stuff like `soft-shadows, AO, glow` are not really possible unless we make BLAS bounds super relaxed, but that comes at the cost of iteration speed
- Beam optimization (pre-pass low-res texture with cone) is not supported because of the same restriction as above

This all seems to hint that we should move away from something like the Vulkan HWRT path, and instead build our own acceleration structure that:
- is automatically updated on the GPU, each frame, depending on the global SDF `d(p)`
- creates tight bounds against the SDF (to reduce iteration count for performance)
- allows querying the distance of a ray to the closest surface (to get some nice effects)

And, ideally, we would have another acceleration structure that would be used to *define* the SDF.
Currently, we are using a simple 3D texture as lookup for intersecting primitives at each voxel, but this has a few problems:
- SDF only stores distances to primitives in close vicinity to them (i.e primitives do not affect the SDF on a "global" scale)
- Scales badly with primitives that have coarse bounds (as they take up more physical space but with empty space most of the time) and with lots of intersecting primitives (slower SDF evaluation)
